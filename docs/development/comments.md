# 日本語コメントの書き方

説明は実装の役割と契約に合わせて記載する。既に読みやすく説明されている箇所は維持し、コードを変更したときに関連する説明も更新する。

## ファイルの説明

JavaScriptは先頭の`@file`に次をまとめる。

- 何のためのファイルか
- どこで動くか（Service Worker、コンテンツスクリプト、ページ側、非表示解析ページ、Nodeなど）
- DOM・Chrome API・保存値・共通モジュールの何を用いるか
- どこまで担当し、他のファイルへ何を委譲するか

```js
/**
 * @file KU-LMSホームへ表示する更新通知の取得状態を管理する。
 * ChromeストレージとGitHubのリリースAPIを使い、日次の取得結果を保存する。
 * 複数タブからの要求を直列化し、通知の重複を防ぐ。表示はコンテンツスクリプトが担当する。
 */
```

CSSは対象ページと対応するクラス・状態を先頭コメントに書く。HTMLは読み込むCSS・スクリプトとページの用途をコメントに書く。

JSONにはコメントを入れられないため、構成の説明はこの資料やREADMEへ記載する。

| ファイル | 用途 |
| --- | --- |
| `manifest.json` | Chromeへ権限、起動スクリプト、注入対象、公開リソースを宣言する |
| `package.json` | 開発用コマンドと依存パッケージを定義する |
| `.htmlvalidate.json` | HTML検査のルールを設定する |
| `.stylelintrc.json` | CSS検査のルールと除外対象を設定する |
| `scripts.config.js` | 機能の設定キー・既定値・注入ファイル・対象URLを共通定義する |

## 関数の説明

名前だけでは分かりにくい処理、共通関数、機能の開始・終了処理にはJSDocを付ける。

```js
/**
 * ローカルタイムゾーンで日次キャッシュに使う日付キーを返す。
 * @param {Date} [date] - キーへ変換する日時。省略時は現在日時。
 * @returns {string} YYYY-MM-DD形式の日付。
 */
```

- 引数は型と役割を書く。時刻・時間・割合は単位を明記する。
- 省略できる引数には`[name]`、単純な既定値には`[name=値]`を使う。
- 設定オブジェクトの分割代入では、必要なプロパティを`options.signal`などで説明する。
- 戻り値は用途を説明し、未検出時の`null`・空文字列・`undefined`を区別する。
- 非同期関数だけでなく、通常関数が返すPromiseにも`Promise<...>`を付ける。
- 例外が呼び出し元の制御に関わる場合は`@throws`に条件を書く。
- 型が入力次第の正規化処理には`*`を使える。型を特定できる戻り値に曖昧な型を付けない。

短いローカルコールバックや明白なテスト用APIの模擬メソッドは、呼び出し元の説明で役割が分かる場合にコメントを重複させない。

## 処理中のコメント

代入やループをそのまま言い直す説明より、実装上の理由を残す。

- 複数タブ・複数機能で共有する状態の所有者
- 取消と認証完了が重なったときの扱い
- DOMのイベント伝播やスクロール復元が必要な理由
- JSFのフォーム更新・ViewState・同名フィールドを保つ理由

新しい説明は日本語にする。API名、識別子、型、正式名称はそのまま記載し、著作権・ライセンスの原文は維持する。外部ライブラリと生成物のコメントは編集しない。
