# Ku-Port取得処理の構成

## 責務と依存方向

| 場所 | 役割 |
| --- | --- |
| `background.js` | Chromeイベント、機能設定、取得ジョブ、キャンセル、保存、待機キュー |
| `background/kuport/syllabus-matching.js` | DOM・Chrome APIを使わない科目名、曜日、時限、教員、学期の照合 |
| `background/kuport/syllabus.js` | シラバスのJSF通信。進捗通知とジョブ確認は呼び出し元から渡す |
| `background/kuport/bulletin.js` | 掲示一覧、全表示、詳細の直列通信。認証後の補助的なセッション確認 |
| `background/modules/kuport-runtime.js` | 専用ログイン画面、既存タブ検出、フォーム・ヘッダー、offscreenの作成・終了 |
| `background/modules/kuport-job-timeouts.js` | 保存済みの開始時刻とChromeアラームによる取得ジョブの期限監視 |
| `background/modules/kuport-form.js` | 文字列フォームをURLSearchParamsにする |
| `features/syllabus.js`, `features/bulletinBoard.js` | KU-LMS上のボタン、一覧、キャッシュ表示、ダイアログ |
| `features/syllabusSessionBridge.js`, `features/bulletinSessionBridge.js` | 所有確認済みの認証用Ku-Portタブから必要なフォームを読む |
| `features/modules/form-utils.js` | DOMのフォーム直列化とaction URL解決 |
| `offscreen/kuportParser.html`, `kuportParser.js` | DOMParserを持たないService Workerから依頼されたHTMLを解析する |

通信モジュールはChromeイベントや保存キーを管理しない。`reportPhase`、`ensureActive`などの
コールバックを渡し、取得順序とジョブ管理を分ける。UIからはruntimeメッセージで取得を依頼する。
ブラウザ用classic scriptとService WorkerのES moduleを混在させない。

## 取得の流れ

1. 設定、年度、待機キュー、既存Ku-Portタブの有無を確認する。
2. 拡張機能専用の最小化ウィンドウで認証する。
3. 専用タブからフォームを受け取り、ウィンドウを閉じる。
4. 機能ごとに必要な画面へPOSTし、offscreenで応答を解析する。
5. 保存と結果通知を行い、解析中の呼び出しがなければoffscreenを閉じる。

Ku-Portの通常タブを読み取ったり通信に再利用したりしない。取得中に通常タブが開かれた場合は中断する。
ブリッジは所有するタブにだけ注入する。子タブの`windowId`からウィンドウ全体の所有権を推定しない。
閉じるのは明示的に作成したウィンドウと追跡しているタブだけ。

offscreenの終了中に次の解析が始まった場合は、終了完了を待ってから新しい解析ページを用意する。
解析中の呼び出しが残っている場合は終了処理を省略する。

### 認証画面の終了とタイムアウト

取得ジョブは認証待ちを含め、開始から2分の期限を設ける。
`chrome.alarms`を使うため、manifestで`alarms`権限を宣言する。
Service Workerの起動時には保存済みジョブの開始時刻を読み、期限監視を復元する。
アラームはPCのスリープなどで遅れる場合があり、復帰後に期限切れの処理を行う。

認証画面のIDはジョブ終了まで保持する。終了操作に失敗して画面が残った場合は、
ジョブを削除せずに再試行する。同じジョブの終了処理は共有し、画面を閉じたときの
タブ削除通知による二重実行を防ぐ。出席率の開始処理は、ジョブ保存前の失敗でも
作成済みの認証画面を終了対象にする。

## 優先順位とキャッシュ

現在の順位は **出席率 → 掲示板 → シラバス**。同順位は先着順。実行中の通信は中断して割り込まない。
シラバス優先と5分間のセッション再利用は保留中で、製品の動作には導入していない。

掲示板の本文はstorage.localに保存する。storage.sessionに取得完了を記録し、同じブラウザ起動中は
再取得しない。次の起動では保存済み本文を表示したまま「更新中」を出す。
失敗時は完了フラグを立てない。拡張機能の再読み込みでもstorage.sessionはリセットされる。
シラバスのキャッシュは30日、最大80件。表示時刻と手動更新はUI側で管理する。
出席率は年度・バージョンを確認して保存済みデータを表示する。

## 変更時の注意点

- JSFのViewStateは応答から更新する。科目や機能をまたいで古いフォームを流用しない。
- 同じKu-Portセッションへ複数のPOSTを並列送信しない。
- サーバーが返した内容はtextContentで表示する。取得HTMLをそのままKU-LMSへ挿入しない。
- 設定キー、メッセージ名、キャッシュ形式は互換性がある契約として扱う。
- `tests/`は回帰チェック、`tools/check-syntax.js`は構文の静的検査。本番起動からは読み込まない。

## 自動ログインとの依存関係（4.5.0）

`background/modules/auth-access.js`が3機能の利用条件を判定する。
自動ログインON、ユーザー名とパスワードの設定済み、一括OFFでないこと、再送制限に達していないことが必要。
認証情報が空の初回導入では、取得用ウィンドウも開かない。TOTPを要求する画面では秘密鍵の未設定を検出して取得を中止する。

画面側は`features/modules/kuport-access.js`から、認証情報を含まない利用可否だけを取得する。
条件を満たさない間は保存済みデータの表示も止める。シラバス・掲示板の設定liを隠し、設定パネルのスイッチを無効にする。
自動ログインをOFFにすると、3機能の保存設定もOFFになる。再びONにした後は必要な機能を個別にONにする。
一括OFFの退避・復元では`FEATURE_SETTINGS_CONFIG`により静的注入の2機能も対象にする。

### 再送制限

- 認証段階（入口、ID、パスワード、OTP等）ごとに送信許可を直列化する。複数タブでも共通の上限になる。
- 同じ段階への送信が10秒内に3回あり、再びその画面へ戻った場合、4回目の自動送信を拒否して停止状態を保存する。
- 遅い再送ループも止めるため、10分内の6回目も拒否する。
- サイトのエラー文を数える方式ではない。成否を判別できない画面でも止められるよう、送信回数で保守的に制限する。
- 履歴と停止状態は`chrome.storage.session`へ送信前に保存する。認証ページの再読み込みやService Workerの停止・再起動では消えない。
- 認証情報の変更、自動ログインの切り替え、ブラウザセッションの終了で解除する。
- 自動送信したタブが認証後の画面へ到達した場合も解除する。既存ホームの再読み込みだけでは別タブの履歴を解除しない。
- 手動ログインは妨げない。診断結果や履歴にはパスワード・Cookie・HTMLを保存しない。

設定の変化は開始前と通信の継続時に確認し、取得中に無効になった場合は所有する画面を片付ける。
画面側も遅れて届いたキャッシュや取得結果でポップアップが再表示されないよう確認する。
